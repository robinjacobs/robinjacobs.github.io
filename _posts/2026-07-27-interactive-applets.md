A plot of a controller response is fine. A plot you can *drag* is better — half the intuition
in control and robotics lives in the derivative of the picture with respect to the parameter,
and you cannot print that.

The constraint is that this site is static. It is a folder of files on GitHub Pages, and there
is no backend to call. So "run Python on the reader's machine" is the only option, which
immediately raises the question of what that costs. A full CPython runtime compiled to
WebAssembly is roughly a 10 MB download and a couple of seconds of boot time. Paying that so
someone can drag a slider over a curve you already know the shape of is a bad trade.

So the applets here run on two tiers, and picking the right one is the whole performance story.

## Tier 1 — Python at build time

Most interactive figures are a sweep over one or two parameters. Nothing about that needs to be
live: the curves can be computed once, offline, and shipped as a table. The browser then does no
maths at all, it just picks a row.

```applet
id: second-order-sweep
title: Step response of a second-order system
runtime: precomputed
data: assets/applets/second-order-sweep.json
height: 340
```

That figure is 29 precomputed damping ratios at 201 samples each — 40 KiB of JSON, generated by
`tools/precompute_applet.py`, which is stdlib-only and runs in about 20 ms:

```python
def step_response(t, zeta, wn=1.0):
    """Unit step response of 1 / (s^2 + 2*zeta*wn*s + wn^2)."""
    if abs(zeta - 1.0) < 1e-9:
        return 1.0 - (1.0 + wn * t) * math.exp(-wn * t)
    decay = math.exp(-zeta * wn * t)
    if zeta < 1.0:
        wd = wn * math.sqrt(1.0 - zeta * zeta)
        return 1.0 - decay * (math.cos(wd * t)
                              + (zeta / math.sqrt(1.0 - zeta * zeta)) * math.sin(wd * t))
    wd = wn * math.sqrt(zeta * zeta - 1.0)
    return 1.0 - decay * (math.cosh(wd * t)
                          + (zeta / math.sqrt(zeta * zeta - 1.0)) * math.sinh(wd * t))
```

Dragging that slider costs one `Plotly.restyle` on an existing trace — no relayout, no rebuild,
no allocation beyond the new `y` vector. It tracks your finger at display refresh rate and it
works with JavaScript that fits in a screenful. Sanity check on the physics: at ζ = 0.05 the
overshoot should be 1 + exp(−πζ/√(1−ζ²)) = 1.854, which is what the curve peaks at.

If a figure can be expressed as "sweep this knob over a range I can enumerate", this tier is
almost always the right answer.

## Tier 2 — Python in the browser, on demand

Some things genuinely cannot be tabulated. Two continuous inputs at a usable resolution already
means tens of thousands of frames, and anything where the reader supplies the *structure* rather
than a parameter is hopeless to precompute.

Below is inverse kinematics for a planar two-link arm. Three continuous inputs — target
position and the length of the first link — so the reachable set changes shape as you drag.
This one really does run CPython and numpy, in your browser, right now.

```applet
id: two-link-ik
title: Two-link arm — closed-form inverse kinematics
runtime: pyodide
height: 420
xaxis: x [m]
yaxis: y [m]
xrange: -2.6, 2.6
yrange: -2.6, 2.6
equal: true
control: x | target x [m] | -2.4 | 2.4 | 0.01 | 1.1
control: y | target y [m] | -2.4 | 2.4 | 0.01 | 0.6
control: l1 | length of link 1 [m] | 0.4 | 1.4 | 0.01 | 1.0
trace: arm | arm_x | arm_y | lines+markers
trace: target | target_x | target_y | markers
trace: workspace | ws_x | ws_y | lines
---
import numpy as np

L2 = 1.0

def compute(x, y, l1):
    reach_max = l1 + L2
    reach_min = abs(l1 - L2)

    # Pull unreachable targets onto the nearest point of the annulus.
    r = float(np.hypot(x, y))
    clamped = min(max(r, reach_min + 1e-9), reach_max - 1e-9)
    if r > 1e-9:
        x, y = x * clamped / r, y * clamped / r
    else:
        x, y = clamped, 0.0

    cos_q2 = (clamped ** 2 - l1 ** 2 - L2 ** 2) / (2 * l1 * L2)
    q2 = float(np.arccos(np.clip(cos_q2, -1.0, 1.0)))
    q1 = float(np.arctan2(y, x) - np.arctan2(L2 * np.sin(q2), l1 + L2 * np.cos(q2)))

    joints_x = [0.0, l1 * np.cos(q1), l1 * np.cos(q1) + L2 * np.cos(q1 + q2)]
    joints_y = [0.0, l1 * np.sin(q1), l1 * np.sin(q1) + L2 * np.sin(q1 + q2)]

    # Both workspace boundaries as one trace, split by a NaN.
    t = np.linspace(0.0, 2 * np.pi, 121)
    ws_x = np.concatenate([reach_max * np.cos(t), [np.nan], reach_min * np.cos(t)])
    ws_y = np.concatenate([reach_max * np.sin(t), [np.nan], reach_min * np.sin(t)])

    reachable = abs(clamped - r) < 1e-6
    return {
        "arm_x": joints_x,
        "arm_y": joints_y,
        "target_x": [x],
        "target_y": [y],
        "ws_x": ws_x,
        "ws_y": ws_y,
        "status": "q1 = %.1f deg, q2 = %.1f deg%s" % (
            np.degrees(q1), np.degrees(q2),
            "" if reachable else " · target pulled onto the workspace"
        ),
    }
```

That code block *is* the applet. There is no build step for tier 2 and no duplicated copy of the
maths — the post is the source.

## What makes the live tier fast

The download is unavoidable, but everything after it is under our control.

**It boots only when asked.** Opening the post costs nothing. Nothing is fetched until you press
*start python runtime*, so readers who scroll past never pay for it.

**One worker, shared by every applet.** The runtime is booted at most once per session and stays
warm across posts. Each applet gets its own Python namespace keyed by id, so a second applet is a
`runPython` call, not another 10 MB. Closing the post tears down the plots and leaves the
interpreter running — reopening is instant.

**It is not on the main thread.** Pyodide lives in a Web Worker. A slow `compute` cannot stutter
the overlay animation or block scrolling; the UI stays responsive while numbers are still coming.

**Results come back as raw buffers.** `compute` returns numpy arrays; the worker converts them to
contiguous float64 bytes and transfers the `ArrayBuffer` to the page with zero copies. Plotly
takes typed arrays directly, so no point is ever boxed into a JavaScript object or serialised
through JSON.

**Slider drags are latest-wins.** A drag emits far more events than Python can service. Rather
than queueing them, each new value replaces the pending one, so the worker computes the frame you
are on now and never spends time on positions your finger has already left.

**Redraws diff.** Updates go through `Plotly.react`, which reconciles against what is on screen
instead of destroying and rebuilding the graph.

The plotting library matters too: this loads `plotly-basic` (~1 MB) rather than the full bundle
(~3.5 MB), because scatter and line traces are all these figures need.

## The budget

| | tier 1 — precomputed | tier 2 — pyodide |
|---|---|---|
| payload | 40 KiB JSON + 1 MB Plotly | + ~10 MB runtime, on demand |
| first frame | immediate | a few seconds, once per session |
| per interaction | one `restyle`, refresh-rate | ~1–10 ms of Python, off-thread |
| authoring | build script writes JSON | Python in the post, no build step |

## Authoring one

An applet is a fenced <code>applet</code> block. The header is `key: value` lines; for the live
tier, everything after a lone `---` is Python that defines `compute(**params)` and returns a dict
of arrays. `control:` lines are `name | label | min | max | step | default`, and `trace:` lines
are `name | x-key | y-key | mode`. Scalars in the returned dict (like `status`) are passed through
as metadata rather than plotted.

The runtime is about 300 lines in `assets/applets.js` and `assets/pyodide-worker.js`. Nothing is
loaded on a post that has no applets in it.

## Where this goes

The obvious next step is letting the reader edit the Python, which the worker already supports —
`register` takes arbitrary source and each applet is namespaced. Beyond that, the interesting
direction is heavier simulation: a cart-pole under LQR, or a trajectory optimiser you can perturb
mid-solve. That is the point at which the WASM download stops being an indulgence and starts
being the only way to put the actual system, not a picture of it, in front of the reader.
